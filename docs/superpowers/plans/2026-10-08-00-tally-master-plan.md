## Commit strategy (100+ meaningful commits)

- One commit per TDD cycle: a failing test plus the implementation that makes it pass, or a separate test commit when the test documents an attack. Never commit a red build to `main`.
- Conventional Commits, with scopes taken from the layout: `core:`, `program:`, `tests:`, `sdk:`, `scripts:`, `app:`, `merchant:`, `ci:`, `docs:`, `release:`.
- Each phase runs on its own branch (`phase/1-program`, …). It's merged to `main` with `--no-ff` after the phase review, so history shows phases as merge bubbles.
- No padding commits: no whitespace-only commits and no splitting one logical change in two. The count comes from the granularity of the work (≈120 planned steps that end in commits).
- Commits carry no AI co-author trailers or attribution lines; author is the repo owner (LSUDOKO).

## Phase gates (definition of done)

1. **Phase 1:** `cargo test --workspace` is green. `cargo build-sbf` succeeds. Every on-chain row of `docs/11-threat-model.md` has a LiteSVM test asserting the exact error. `pay_offer` CU is recorded (target < 45,000 without PoW). Fixtures are committed.
2. **Phase 2:** the program is deployed to devnet. `pnpm seed-demo` creates a merchant, menu and capsule. One paid and three reverted transactions are visible on Explorer. CI is green.
3. **Phase 3:** a release APK installs on a device, and the honest purchase, Whisper co-sign, payee-swap revert and NFC tap all work end to end on devnet. The Kotlin unit tests reproduce `fixtures/menu-v1.json` byte for byte.
4. **Phase 4:** the GitHub Release has the signed APK, checksums and notes. The README has the demo video link, APK link, program ID and build steps. The deck PDF is in `deck/`. The submission checklist in `docs/13` is complete.
